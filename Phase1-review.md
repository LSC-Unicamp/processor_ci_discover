# Phase 1 implementation review

Reviewed on 2026-11-25 against `Roadmap.md`, the repository README, the current working tree, and `python -m pytest -q` (26 passed). The roadmap checkboxes mark only completed items. Phase 1 does **not** meet its exit criteria yet.

## Blocking gaps

1. **Candidate configurations are not exported.** `try_incremental_approach()` records failed attempts but explicitly defers writing their configs (`core/config_generator.py:473-477`). `save_failed_candidate_config()` exists in `core/config.py` but has no caller. The final path writes only the canonical config (`core/config_generator.py:1482`); therefore requested, first heuristic, and fallback candidates never become distinct files. Its fixed `<repo>.json` name would also overwrite earlier candidates if called repeatedly.
2. **The first heuristic candidate is lost or mislabeled when a requested top is supplied.** `interactive_simulate_and_minimize()` prepends the override to the ranked list (`core/config_generator.py:576-583`), while the Verilator and GHDL loops label every other candidate `fallback` (`core/config_generator.py:422-430`, `runners/ghdl_runner.py:1235-1243`). No `first_heuristic` role or heuristic rank is retained in that case. When requested and ranked tops coincide, deduplication uses only `(top_module, top_file)` and never merges roles. It omits build context and parameters, contrary to the roadmap identity rule.
3. **A missing requested top has no attempt result.** The override is skipped if absent from `module_to_file` (`core/config_generator.py:584-587`); the test `test_missing_override_falls_back_to_ranked_candidate` expects only the heuristic attempt. The roadmap requires a retained partial result for every supplied top.
4. **Failure evidence is incomplete.** Both runner adapters create results with empty `errors`, `log_path=None`, and approximate command strings (`core/config_generator.py:437-471`, `runners/ghdl_runner.py:1263-1303`). The final writer stores only `last_log` as `requesting.log` (`core/config_generator.py:1494-1502`), so earlier failed attempt logs and exact commands are lost. It sets `candidate_result.log_path` even though `candidate_result` is only assigned inside the `if not run_context.candidates` branch (`core/config_generator.py:1450-1465`); this is caught and logged, leaving the report without a linked log.
5. **Success is overstated.** A Verilator return code of zero is recorded as `status="success"` and `is_simulable=True` (`core/config_generator.py:431-458`), although the runner path is incremental compilation/lint rather than a built and executed smoke simulation. GHDL likewise records compilation success (`runners/ghdl_runner.py:1246-1282`). The roadmap requires successful, failed, and inconclusive validation to be distinct and the validation gate to be explicit.
6. **The candidate limit is not enforced.** `--max-candidates` is stored and reported but the Verilator loop hardcodes ten attempts (`core/config_generator.py:331-337`), and neither runner selects up to three promoted distinct candidate configs. A full report may include more attempts, but export needs an independent three-candidate selection rule.
7. **No-success output can leave a stale usable config.** `save_usable_config()` declines to write a failure, but `generate_processor_config()` does not remove or invalidate an earlier `<repo>.json` at the same path (`core/config_generator.py:1482-1484`). A later failed run can therefore appear usable to downstream readers. CLI `main()` also returns `None` for a failed discovery (`cli.py:108-111`), so the exit status does not distinguish no success.

## Other gaps and compatibility risks

- `is_usable_config()` accepts a schema 2.0 config with no `discovery` block when it has a top and files (`core/config.py:91-115`), despite the documented validation guard. Chisel writes before adding discovery metadata (`core/config_generator.py:1109-1120`), and the generator branches do not consistently add the canonical schema/default fields.
- Canonical RTL output still sets `march="rv32i"` and `two_memory=false` (`core/output.py:25-26`), but there is no default provenance and failed standalone candidate configs do not exist. The roadmap defaults item remains open until all exported paths are covered.
- Ollama code was removed from the core workflow, but `requirements.txt:20` still pins `ollama`, and `README.md:35-86` documents removed `-n`, `-m`, and `no_llama` interfaces. Remove or update these before claiming the broader Ollama removal decision complete.
- Existing tests check override ordering, one fallback, and canonical output. They do not assert three exported candidates, merged roles, complete failed evidence, no-success disk state, or VHDL attempt reports. The CLI test allows `--max-candidates 5`, which does not verify the export cap.

## Suggested completion order

1. Define one candidate identity and role merge function, preserving the independently ranked first heuristic top and a partial result for unresolved requested tops.
2. Capture each real command, source set, diagnostic, validation level, and log before moving to the next attempt; write the report even when discovery fails.
3. Select and export up to three distinct candidate configs, with unique names, while publishing the canonical config only for a verified validation gate. Clear or explicitly invalidate stale canonical output on failure.
4. Add behavior tests for every Phase 1 scenario in the roadmap, including actual output files and report contents, then update README and dependency metadata.
